## 1. 背景と目的

| | 現状 | 移行後 |
|---|---|---|
| 営業情報の入力 | Google カレンダー（`oominami2026@gmail.com`）に予定として手入力 | **このアプリの管理画面**で入力（定義から自動作成＋例外だけ手修正） |
| 入力している人 | システム管理者（オーナーへの移管が困難） | **オーナー・管理者** |
| HP埋め込み表示 | `oominami-calendar`（Google Calendar API から描画） | このアプリの公開ページ（iframe の `src` を差し替え） |
| A4ポスターPDF | `oominami-calendar` の `?poster` | このアプリの管理画面から出力 |

Google カレンダーでは「時刻あり＝営業」「終日＝イベント」「複数日＝帯」「タイトルに休業＝赤」
という暗黙のルールで入力する必要があり、慣れない人には難しかった。新機能では
「区分ごとの営業時間の定義」から毎月自動で作り、**いつもと違う日だけ**をボタン操作で直す。

## 3. 要件

### 3.1 営業時間の定義
- 区分は **月〜木 / 金 / 土 / 日 / 祝 / 祝前日** の6つ。区分ごとに次を持つ。
  - 営業する／定休
  - 開店時刻（前日から通しで続いている日は使わない）
  - 閉店時刻 **または**「翌日まで通し（お泊まり可）」
- 通し営業が続く日は**1本の帯**として表示する
  （例: 金10:00〜 → 土 → 日〜24:00 ＝「初日10〜通し」…「〜最終24」）。

**区分の判定順（決定）**
1. 翌日が祝日 → **祝前日**
2. その日が祝日 → **祝**（ただし**金・土の祝日は除く**）
3. それ以外 → 曜日（月〜木 / 金 / 土 / 日）

- 金・土が祝日の日（例: 2028/2/11 金・建国記念の日）は、区分は「金」「土」で**通し営業**。
  `holiday_name` は保存するので、**日付は祝日として赤字**で表示される。
- 定義画面の「区分の決まり方」にもこの扱いを明記する。

> 添付のHP画像（2026年9月）で検証済み: 9/20(日)〜9/22(火・祝)は翌日が祝日なので「祝前日＝通し」、
> 9/23(水・祝)は「祝＝〜24」。週末の帯・平日 10〜24・泊まり可能の位置も一致する。

### 3.2 営業カレンダーの作成と例外変更
- **毎月15日に翌々月1ヶ月分**を定義から自動作成（例: 9/15 に11月分）し、管理者へ通知。
- 作成後〜**月末まで**に例外（臨時休業・時間変更・イベント）を手で直す。
- **翌月1日になると、確認の有無にかかわらず**「翌月」としてHPに公開（HPは従来どおり今月＋翌月まで）。
- 公開後の月も変更可能（急な臨時休業など。変更は即時にHPへ反映）。
- 営業時間とは別に**イベント・お知らせ**（単日／複数日）を載せられる。**種類ごとに色分け**。

### 3.3 インタフェース
- **日をタップ → 「いつもどおり／時間を変える／臨時休業」の3択**。
- 手で変えた日は印（●）が付き、「いつもの設定に戻す」でいつでも戻せる。
- HP表示用カレンダーを**管理画面内でプレビュー**（公開前の月も確認できる）。

### 3.4 月の状態（アプリ全体の配色原則に合わせる）

| 状態 | 意味 | 色 |
|---|---|---|
| 未作成 | 15日の自動作成前 | グレー |
| **準備中** | 作成済み・まだHPに出ていない（翌々月） | **イエロー**（未確定） |
| **公開中** | 今月・翌月（HPに表示中） | **グリーン**（確定） |
| 終了 | 過去の月 | グレー |

状態は日付から自動で決まる（確認操作は無い）。準備中の月には
「9月30日（あと13日）までに直してください。10月1日から自動で公開されます」を表示する。

## 4. 業務の流れ（月次サイクル）

```
 15日 03:00  システム: 翌々月分を定義から自動作成
             → 管理者へ Web Push「11月の営業カレンダーを作成しました。9月30日までに…」
    │        （タップで該当月の営業カレンダーが開く）
    ▼  〜月末
 オーナー・管理者: 準備中の月を開き、例外だけ直す（臨時休業・時間変更・イベント）
                   「ホームページでの見え方」で確認
    ▼
 翌月1日   自動的にHP公開範囲に入る（今月＋翌月）
    ▼  随時
 公開中の月も必要に応じて変更（即時反映）／A4ポスターPDFを出力して掲示
```

## 5. データベース設計（Supabase・マイグレーション追加）

時刻は**その日の0:00からの分**で持つ（`600`=10:00、`1440`=24:00、`1740`=翌5:00）。
既存カレンダーの「24〜29」表記・深夜跨ぎの扱いと相性がよい。

### 5.2 RLS・関数
- 上記テーブルは**管理者のみ**読み書き（`is_admin()`）。`jp_holidays` は管理者 select のみ（書き込みは関数経由）。
- `public_business_calendar(p_from date, p_to date)`（SECURITY DEFINER・**anon 実行可**）
  - `p_to` を **JSTの翌月末で頭打ち**にし、準備中の月は返さない。
  - 返すのは営業情報（`date, holiday_name, status, open_min, close_min, overnight`）と、
    `is_public` のイベント（タイトル・期間・種類名・色）、凡例用の種類一覧のみ（メモ・更新者は返さない）。
- 変更はすべて `log_activity` に記録（例:「営業カレンダー変更 11/13 臨時休業」）。
- `app_settings` に `notify_business_calendar`（既定 `true`）を追加。

## 6. 作成処理と通知（DB内で完結させる）

> ⚠️ 当初案（APIルートで作成）から変更。このアプリは **service_role キーを持たない**ため、
> cron から呼ばれるAPIルートはDBを読み書きできない（design.md「未打刻通知」の設計方針）。
> 既存の未打刻通知と同じく、**判定・作成・送信先の解決はSQL、APIルートは Web Push の暗号化と送信だけ**にする。

### 6.1 祝日データの取得
- `pg_cron`（毎日 02:00 JST）→ `pg_net` で holidays-jp（`https://holidays-jp.github.io/api/v1/date.json`。前年〜翌年分）を GET。
- `pg_cron`（毎日 02:30 JST）→ レスポンス（`net._http_response`）を読み `jp_holidays` に upsert。
- 失敗しても前日までのデータが残る。**対象月の年の祝日が1件も無ければ作成を中止**し、
  管理者へ「祝日データを取得できていません」と通知する（祝日なしで誤作成しないため）。

### 6.2 作成
- `generate_business_month(p_ym date)`（SECURITY DEFINER）
  1. 対象月の各日の区分を §3.1 の判定順で決める（翌月1日の祝日も参照）。
  2. 定義を当てはめて `business_days` を作る。
  3. 既存行があれば **`is_manual = false` の行だけ置き換え**（手で直した日は残す）。
  4. `business_months` に記録。
- 管理画面から呼ぶときは `is_admin()` を確認。**未作成の月ならどの月でも作成可**（移行テストで10月・11月を作るため）。
- 定義を変更したとき: 「準備中の月に反映しますか？（手で直した日はそのまま）」を確認して再作成。

### 6.3 自動作成と通知
```
pg_cron（毎日 03:00 JST）→ create_business_month_if_due()
  └ JSTで15日以降 かつ 翌々月が未作成 → generate_business_month()
      └ notify_business_calendar が true かつ notified_at が null
          → 管理者の push_subscriptions を集め pg_net で POST /api/notify/business-calendar
          → notified_at を記録
```
- **毎日判定＋冪等**なので、15日に止まっていても翌日以降に追いつく。通知も1回だけ。
- 通知文: 「11月の営業カレンダーを作成しました」「9月30日までに、臨時休業・営業時間の変更・イベントを設定してください。10月1日からホームページに表示されます。」
  タップで `/admin/calendar?ym=2026-11` を開く。
- 送信APIは `src/app/api/notify/business-calendar/route.ts`（`api/notify/punch` と同じ形）。
  Vault に送信先URL `notify_business_calendar_url` を追加（`notify_secret` は共用）。DR手順にも追記。
- **アカウント設定 > 通知 > 通知対象（管理者向け）** に4つ目のスイッチ「営業カレンダーの作成」を追加。
- 通知を受けるには、オーナーの端末でも「この端末で通知を受け取る」を有効にしておく（iPhone はホーム画面に追加したアプリから）。

### 6.4 表示用の整形（`src/lib/business-calendar-view.ts`）
移行元 `normalize.ts` の考え方を移植し、**vitest で網羅テスト**する。
- 連続する通し営業を1つにまとめ、週ごとに帯へ分割。先頭「初日10〜通し」／末尾「〜最終24」。
- 単日は「10〜24」（分00省略、24〜29表記）。
- `temp_closed` は赤チップ「臨時休業」、通しの日に「泊まり可能」チップ。臨時休業の日で帯が途切れる。
- イベントは種類の色で表示。凡例は「営業時間」＋種類ごとの色。
- SQL側の区分判定とTS側の結果が一致することを、2026年9月（添付画像）・11月のデータで確認する。

## 7. 画面構成

### 7.1 管理画面（管理者のみ）
| パス | 画面 | 主な操作 |
|---|---|---|
| `/admin/calendar` | **営業カレンダー**（メイン） | 月タブ（状態つき）、月グリッド、日をタップして例外編集、イベント追加（種類を選ぶ）、未作成月の「今すぐ作成」 |
| `/admin/calendar/patterns` | **営業時間の定義** | 6区分を1行ずつ（営業／開店／閉店 or 翌日まで通し）。区分の決まり方と注意、9月連休での結果例 |
| `/admin/calendar/preview` | **ホームページでの見え方** | HPと同じ表示（準備中の月も可）、PC/スマホ幅切替、A4ポスターPDF/画像、埋め込みコード |
| `/admin/settings`（追加セクション） | **イベントの種類と色** | 種類の追加・名前変更・色の選択・削除 |
| `/admin/account`（既存に1項目） | **通知対象** | 「営業カレンダーの作成」スイッチ |

- サイドバー「管理」グループに「営業カレンダー」を追加。「関連情報 > 営業カレンダー」の外部リンクは新しい画面へ差し替え。
- スマホは月グリッド＋**下からのシート**で日編集、PCは**右パネル**（スキル `mobile-calendar-ui` の master-detail パターン）。

### 7.2 公開・従業員
| パス | 用途 | 認証 |
|---|---|---|
| `/calendar/embed` | **HP埋め込み用**（移行元の表示を移植。今月＋翌月） | 不要（anon RPC） |

- `/calendar/embed` は**静的ページ＋ブラウザから Supabase RPC を直接呼ぶ**構成にし、HPの閲覧でWorkerのCPU/リクエスト枠を消費しないようにする。middleware の公開パスに追加。
- 従業員画面は現状のまま（メニューの「営業カレンダー」リンク先だけ新URLに差し替え）。

## 10. テスト観点
- 区分判定: 祝前日の連続（9/20〜9/23）、**金・土の祝日が金・土の区分（通し）かつ日付赤字**（2028/2/10〜2/13 で確認）、月末日の翌日が祝日（翌月の祝日参照）、年をまたぐ月。
- 帯: 週またぎ・月またぎ（前月末の通しから始まる月）・臨時休業で途切れる通し。
- 作り直し: 手で変更した日が残ること。定義変更→準備中の月だけ作り直し。
- 自動作成: 15日より前は作らない／15日以降に1回だけ作る／通知が1回だけ届く／スイッチOFFで通知しない／祝日データ無しで作成中止。
- 公開範囲: anon で準備中の月・非公開イベント・メモが取得できないこと。1日になった瞬間に翌月が見えること。
- イベントの種類: 色変更が管理画面・埋め込み・ポスターに反映、種類削除時は既定の種類で表示。
- 表示: iPhone幅でチップが切れない、PDF の文字切れ・崩れ（移行元の検証手順を流用）。
