## 1. 目的

お客様の入店状況(店内の人数・滞在時間・客層)をリアルタイムで見える化し、混雑やクレームをオーナーのスマホに通知する。

## 2. 業務の流れ(現場スタッフ・受付)

- 入店時: 受付番号を入力し、客層分析のために年齢層と特徴(既定の分類から選ぶ。分類はオーナーが別途指定)を選ぶ。
- 退店時: 受付番号を入力する。番号を打つとその番号の入店時刻と滞在時間を表示し、確かめてから記録。店内にいない番号はその場で知らせる。
- 要望・クレーム: 受付番号(わかれば)・分類・内容をその場で登録する。

## 3. 管理機能(オーナー・管理者)

| 画面 | 内容 |
|---|---|
| いまの店内 | 現在の入店者数(入店後・未退店)、当日の入店累計、平均滞在、長時間滞在(例: 3時間超)の人数、店内の客層の内訳、滞在の長い順の一覧。開いている間は自動で更新 |
| 時間帯別の推移 | 時間帯別の入店者数(棒)と店内の人数(折れ線)。当日と指定日 |
| 日別の推移 | 日別の入店総数。週・月で切り替え |
| 要望・クレーム | 未対応 → 対応中 → 完了の状態、対応した人と内容の記録、分類ごとの件数 |

## 4. 通知(オーナーのスマホ。既存の Web Push と同じ仕組み)

| 内容 | タイミング |
|---|---|
| 現在の入店者数 | 指定した間隔ごと(営業時間中だけ) |
| 入店者数が指定人数を上回った | 即時 |
| 入店者数が指定人数を下回った | 即時 |
| クレームの発生 | 即時 |
| 要望 | 1日1回まとめて(例: 閉店後 22:00) |

- 上限・下限の前後を行き来しても続けて鳴らないよう、一度知らせたら人数がいったん戻るまで同じ通知は出さない。
- 間隔・人数・時刻・受け取る人(オーナーと、オーナーが指定した従業員。システム管理者は選べない)は設定画面で変えられる。
- 定時の通知は、無料プランの CPU 上限(§32)を考えて DB 側(pg_cron)で動かす想定。

## 5. システム管理者には数値と内容を伏せる(2026-10-26 検討)

オーナーは店の内情をシステム管理者に見せたくない想定。ただしシステム管理者は画面の表示具合・レイアウトを確認したい。

- 従業員の個人情報(`employee_profiles_for_admin()`。design.md「権限の分離(2026-10-11)」)と同じく、**DB の中で伏せ字にして返す**。
  システム管理者の端末には本当の値が届かない。
- 見出し・ボタン・表とグラフの枠・横軸の時刻と日付は表示。人数・時刻・客層・内訳の比率・縦軸の目盛り・折れ線・要望/クレームの区別・件数・日時・本文・対応内容は伏せる。
  グラフの棒は同じ高さの網かけ、内訳の帯は均等幅の網かけ。画面の上に「システム管理者の表示：数値と内容は伏せています」の帯。
- **限界**: Supabase のダッシュボード・SQL・バックアップ(GitHub の backups リポジトリ)からは技術的に見える。個人情報と同じく「アプリでは見せない・直接見ない」運用上の約束になる。
- より強くする案: 要望・クレームの本文をオーナー・従業員の端末で暗号化してから保存(DB・バックアップでも読めない)。合言葉をなくすと読めなくなる・作業量が増える。
  人数は通知のために DB で数える必要があるので、この方法では隠せない。

## 6. 作り方

- **経費管理と同じ作り**(design.md §31): 給与管理と同じアドレスの下(例: `/visit`)で動かし、ログイン・端末承認を共通にする。
  経費管理と同じく別の Worker にしてサービスバインディングで中継するか、給与管理の中に作るかは着手時に決める。
- メニューの「経費へ」と並べて「入店管理へ」(アプリ切り替えの見た目。テーマ色は給与の紺・経費のグリーンと区別する新しい色。資料では仮にえんじ `#5a2342`)。
  入店管理からは「給与管理へ」で戻る。
- マニフェストの id・scope・start_url を入店管理のパスにして、単独でホーム画面に追加できるようにする(受付の iPad 用)。
- 受付の端末では入力画面だけ、管理者には管理画面と通知の設定も表示する。
- 新しいテーブルには同じマイグレーションで権限を明示する(CLAUDE.md。`anon` には開けない)。
- 店内の一覧・グラフはブラウザから読む(全件をサーバーで埋め込まない。§32)。

## 7. オーナーに判断してもらうこと

1. この内容で作り始めてよいか
2. 年齢層の区分と特徴の分類(資料では「20代以下〜60代以上」「初来店・常連・お一人・グループ・カップル・海外の方」を例にした)
3. 受付番号の決め方(番号札の使い回しか、毎日1番からか。使い回す場合は店内にいる間は重ならない運用)
4. 退店の入力漏れの扱い(閉店時にまとめて退店にするか、管理者が確認して直すか)
5. 通知の初期値(定時報告の間隔、上限・下限の人数、要望のまとめの時刻、受け取る人)
6. 受付で使う端末(店の iPad の共有アカウントを想定)
7. システム管理者に伏せる範囲(伏せ字だけか、本文の暗号化までか)と、管理画面を見られる従業員(店長など)
